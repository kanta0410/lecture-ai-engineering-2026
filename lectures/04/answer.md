# 第4回 解答

## 演習

- 取り組んだレベル：基礎
- やったこと：自分で付けた評価ラベルと、LLM に付けさせた評価ラベルを比較した。LLM の評価で unsure（要確認）になった項目について、LLM がよりはっきり判定できるように評価基準を定め直した。
- 基準別の一致率（直す前）：根拠 9/10、範囲 9/10、ヒント 9/10、分かりやすさ 8/10、回の表示 6/10
- 要確認の件数（直す前）：1件
- 直した基準と、書き足した方針：用語集にないことを伝えたうえで一般的な説明をしている場合は、根拠なしと判断する方針を根拠の基準に追加した。ただし、用語集にない語であることを伝えたうえで一般的に説明することは、断定ではないため pass とする方針も書き足した。
- 基準別の一致率と要確認の件数（直した後）：要確認 0件
- 講師のラベルと自分のラベルで判定が違った項目と、そう判定した理由：講師ラベルと自分のラベルで判定が異なる項目があった。特に第10回の判定ヒントや回の表示については、判定ヒントが何を表しているのかを十分に理解できていなかったため、自分の判断が講師のラベルと異なった。
- 気づき・疑問：曖昧な回答を無理に pass / fail と断定させず、曖昧なら曖昧であると明確に書かせることが重要だと感じた。最初は LLM に評価させ、unsure になった部分だけに具体的な判断基準を追加していく進め方がよいと思った。また、判定ヒントが何を表すのかを理解したうえで、より正確にラベルを付けられるようになりたい。第10回ではヒントを分かりやすくし、回の表示もすべてオフにした。

## 宿題

- 取り組んだレベル：基礎 / 実装 / 発展
- やったこと：
  - 基礎では、`data/eval/rubric.md` の「分かりやすさ」に「同じ内容の言い換えや繰り返しが1箇所でもある場合は fail とする」と追加し、変更前後で同じ10件を採点した。
  - 実装では、質問と期待するふるまいを10件作り、第3回のエージェントに回答を生成させ、人間のラベルとLLM-as-a-Judgeの判定を比較した。
  - 発展では、顧客対応エージェントのベンチマークである τ²-Bench を調べた。
- 結果：
  - 基礎の分かりやすさの一致率は 6/10 から 7/10 になり、総合の一致率は 7/10 のまま、要確認は 0 件のままだった。
  - 実装の一致率は、根拠 8/10、範囲 9/10、ヒント 10/10、分かりやすさ 6/10、回の表示 4/10、総合 5/10 だった。自作ケースの多くで回答末尾の「第N回」を扱わなかったため、回の表示の一致率が低くなった。
  - 発展で読んだデータセットは [τ²-Bench](https://arxiv.org/abs/2506.07982) で、公式リポジトリは [sierra-research/tau2-bench](https://github.com/sierra-research/tau2-bench) である。
  - 具体例として、海外にいるユーザーのモバイルデータが使えない問題を読んだ。エージェントが契約側のローミングを有効にし、ユーザーが端末側のローミングを切り替え、最後にモバイルデータが使えて通信速度が excellent になったかを環境状態で確認する課題である。ユーザーがすぐに解決できない場合は、少し不満を示すというペルソナも含まれている。
  - 論文の著者は5人で、Sierraを中心にUniversity of Toronto・Vector Instituteと共同研究している。作成手順は、LLMでデータベース・ツール・テスト・ポリシーの草案を作り、ユニットテストが通るまで人が手動で修正し、原子タスクをプログラムで組み合わせて検証可能なタスクを生成する流れである。人間の確認人数と不採用にした問題数は論文に明記されていなかった。
  - 今日の評価セットは回答文を人とLLMが採点するものだったが、τ²-Benchはユーザーのペルソナ、ユーザー側の端末ツール、エージェント側のツール、最終的な環境状態まで含めて評価する点が異なる。
- 気づき・疑問：
  - ベンチマークでは、回答文が自然かだけでなく、ユーザーと協力してツールを正しい順番で使い、最後の状態を正しく変えられたかを評価している点が面白いと感じた。LLMで草案を作っても、テストと人の手動修正を組み合わせて信頼性を確認していることが分かった。
